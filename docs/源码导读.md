# 中医药命名实体识别源码导读

下面按程序实际执行顺序读。每一站都给出调用者、传入的数据，以及结果交给谁。示例原文用「口苦，晨起又口苦」，假定金标只标第二处「口苦」。

## 1. 训练时，一条样本怎么走到最佳适配器

### 第一步：从命令行到原始样本

打开 [train.py](../train.py)，从文件末尾的 `main()` 往回找。它先调用 `load_config()` 读取配置，用命令行参数覆盖指定配置项，然后把配置、实验名和可选的样本数量限制交给 `run_training()`。

在 `run_training()` 里沿前三次调用走。配置校验通过后创建实验目录，再调用 `_load_training_samples()`。这个函数从配置指定的目录读取三份 JSONL，校验样本并检查跨集合原文重复。返回给训练流程的 `samples` 只保留 `train` 和 `dev`。测试集在这里参与数据检查，最终测试从评估入口单独执行。

此时样本仍是普通字典。示例的关键字段是：

```json
{"id":"dev-example","input":"口苦，晨起又口苦","output":[{"text":"口苦","type":"临床表现","start":6,"end":8}]}
```

真实数据还带有任务指令 `instruction`，可对照 [实际开发集](../data/processed-exam-results/dev.jsonl) 第一行和 [Sample 类型](../ner_types.py)。

### 第二步：从带坐标的金标到训练张量

回到 `run_training()`，看它如何把 `load_base_model()` 返回的分词器和模型交给 `_encode_training_samples()`。后者逐条调用 [model_runtime.py](../model_runtime.py) 的 `encode_sample()`：

1. `build_prompt(sample)` 将指令和原文组装成提示。分词器把提示变成 `prompt_ids`。
2. 因为「口苦」在原文的起点分别是 0 和 6，金标起点 6 对应第 2 次出现。编码器将答案写成 `[{"text":"口苦","type":"临床表现","occurrence":2}]`，分词后追加结束符，得到 `answer_ids`。
3. 返回的 `input_ids` 是提示和答案的拼接。对应的 `labels` 将提示位置填成 `-100`，答案和结束符位置保留实际 token ID，损失只在后者计算。
4. 回到 `_encode_training_samples()`，它检查答案长度、生成预算和模型上下文容量，返回按集合组织的 `features` 和长度统计 `lengths`。

继续往下，`run_training()` 调用 `add_lora()` 挂载适配器，把长度统计写入实验环境记录，再把模型、分词器、`features` 和原始 `samples` 一起交给 `_create_trainer()`。这里顺手对照两行参数：`eval_dataset=features["dev"]` 负责常规验证损失，`raw_eval_samples=samples["dev"]` 负责接下来的自由生成。
意思是：同一份 dev 验证集，用两种数据形式，分别做两种评估。
| 参数    	| 数据形式	| 用来评估什么 |
eval_dataset=features["dev"]	  已经过分词、编码的数据，包含输入和标准答案标签	 计算验证损失 eval_loss
raw_eval_samples=samples["dev"]	原始文本和标注实体	让模型生成答案，再计算实体级 Precision、Recall、F1

### 第三步：从验证回调到模型选优

`run_training()` 执行 `trainer.train()` 后，训练和每轮结束的验证由 Hugging Face Trainer 调度。仓库的连接点在 [ner_trainer.py](../ner_trainer.py) 的 `EntityTrainer.evaluation_loop()`：

1. 调用父类验证循环，使用编码后的验证集计算损失。
2. 把当前模型、分词器、原始开发集和生成预算交给 `generate_records()`。它只把提示送入模型，答案由模型生成。具体生成过程见下一节。
3. 把返回的记录交给 `score_predictions()`，保存到实验目录的 `validation/step-<步数>/`。`flatten_metrics()` 将结果展开，并把 `eval_entity_micro_f1` 放回 Trainer 的指标字典。（[ner_trainer.py (line 75)](/Users/wangmeiling/Documents/py_workspace/tcm-ner/ner_trainer.py:75)：output.metrics.update(flatten_metrics(report, metric_key_prefix)) 将计算出的实体指标补充到父类评估结果 output.metrics 中。）
4. 回看 `_create_trainer()` 中的 `metric_for_best_model` 和 `load_best_model_at_end`。前者正好指向上一步写回的指标，后者让 Trainer 在训练结束时恢复最佳权重。`trainer.train()` 返回后，`_save_training_result()` 把恢复的适配器、分词器和运行配置保存到 `best_adapter/`，把最佳 checkpoint 写入 `summary.json`。  （用它选择最佳模型：[train.py (line 228)](/Users/wangmeiling/Documents/py_workspace/tcm-ner/train.py:228)：
metric_for_best_model="eval_entity_micro_f1",
greater_is_better=True,）

我的问题：metric_for_best_model="eval_entity_micro_f1", 这个是不是属于回调？
不是，`metric_for_best_model="eval_entity_micro_f1"` **属于 Trainer 的训练参数配置，不是回调**。

它告诉 Trainer：**比较模型好坏时，使用评估结果中的 `eval_entity_micro_f1` 指标。** 配合本项目的：

```python
greater_is_better=True,        # F1 越大越好
load_best_model_at_end=True,   # 训练结束后加载最佳模型
```

本项目的流程是：

1. 自定义 `EntityTrainer.evaluation_loop()` 计算实体 F1，并加入指标字典。
2. Trainer 根据 `metric_for_best_model` 指定的键读取 F1，判断哪个 checkpoint 最好。
3. 训练结束后恢复最佳模型。

**回调**则是通过 `TrainerCallback` 在某些事件发生时执行逻辑，例如 `on_evaluate`（评估完成时）、`on_save`（保存时）。早停常通过 `EarlyStoppingCallback` 实现，它也可以读取这个配置，但配置本身不是回调。

回调和钩子 是一个意思吗？
意思接近，但侧重点不同：

- **回调（callback）**：你提供一个函数或对象，交给框架，由框架在合适的时候调用。
- **钩子（hook）**：框架预留的扩展位置，让你在特定阶段插入逻辑。

在 Trainer 中：

```python
class MyCallback(TrainerCallback):
    def on_evaluate(self, args, state, control, **kwargs):
        print("评估结束了")
```

这里：

- `MyCallback` 是你注册的**回调对象**。
- `on_evaluate` 是“评估结束时”这个**钩子方法**。
- 评估结束后，Trainer 调用这个方法，执行你的逻辑。

所以日常交流中两者经常混用。更准确地说：**钩子强调“在哪里执行”，回调强调“交给框架调用什么”。**

本项目重写的 `evaluation_loop()` 属于通过继承扩展评估流程，没有使用 `TrainerCallback` 回调机制。


## 2. 预测时，模型输出怎么还原成原文位置

打开 [predict.py](../predict.py) 的 `main()`。它调用 `load_adapter()` 读取 `best_adapter/runtime.json` 并加载模型，然后将 `{"id":"predict-1","input":原文}` 包成单元素列表，连同运行配置里的指令与长度预算传给 [generate_records()](../model_runtime.py:172)。训练验证和单条预测都走这个函数。

顺着 `generate_records()` 的循环看四个中间值：

| 中间值 | 从哪里来，交给谁 |
| --- | --- |
| `batch` | 当前一批样本。用 `build_prompt()` 逐条组装提示 |
| `prompts` | 左填充后的 token 张量和注意力掩码。检查上下文预算后传给 `model.generate()` |
| `outputs` / `raw` | 从生成序列切掉整段批次输入，找到首个结束符，再解码剩余部分。此时 `raw` 是模型生成的 JSON 字符串 |
| `parsed` / `records` | 调用 `parse_prediction(原文, raw, ...)` 解出实体。生成记录保留输入、原始输出、解析结果和诊断信息，再返回调用者 |

继续跳进 [parse_prediction()](../ner_utils.py:215)。如果模型输出 `[{"text":"口苦","type":"临床表现","occurrence":2}]`，它先解析 JSON，再由 `occurrence_starts()` 得到 `[0, 6]`，取第二项并加上实体长度 2，得到 `[6, 8)`。随后用 `valid_entity()` 确认类别和原文切片，用 `entity_key()` 去重。`predict.py` 拿到第一条记录后，将实体与诊断字段打印为 JSON。训练验证则把整批记录交给评分函数。

## 3. 评估时，同一份预测怎么换一版标注重算

打开 [evaluate.py](../evaluate.py) 的 `main()`，定位 `if args.predictions`。两条分支最后都会向 [score_predictions()](../ner_utils.py:279) 提供同一种关键信息：原文、金标 `output` 和原始生成 `raw_output`。

- **现场生成**从 `--data` 读取并校验样本，用 `load_adapter()` 加载模型。内部的 `generate()` 把样本及元数据转交给 `generate_records()`。若启用补查实验，会用另一种提示生成第二轮，再由 `merge_recheck()` 把解析通过的目标类别实体并入首轮。
- **离线复算**从 `--predictions` 读取已有记录。若同时给了 `--data`，按 ID 建立索引并核对 ID 集合和每条原文。从新数据取金标，从旧预测取指令、`raw_output` 和生成上限标记，再组装评分记录。

走进 `score_predictions()`，看到它从 `raw_output` 重新解析实体。每条记录用 `entity_key()` 形成金标和预测两个集合。若模型把示例的第二处「口苦」猜成第一处，预测集合里的 `("临床表现", 0, 2)` 贡献一个 FP，金标集合里的 `("临床表现", 6, 8)` 贡献一个 FN。解析失败按空预测处理，非法条目还会影响误报计数。最后，`_metrics()` 根据汇总计数算出 Micro-F1，由外层入口保存预测和指标。

这就是[结项报告](结项报告.md)中两份开发集的连接方式。训练用 `dev.jsonl` 选出第 1032 步适配器，再用 `dev-clinical-reviewed.jsonl` 和该步的已有预测离线复算。复核版验证集 Micro-F1 为 **83.66%**，测试集为 **77.49%**。

## 4. 往上游追，基础 JSONL 是怎么来的

从 [prepare_data.py](../prepare_data.py) 的 `main()` 进入 `prepare_data()`。它为训练、开发、测试三个集合分别调用 [ner_utils.py](../ner_utils.py) 的 `read_bio()`。阅读时跟着一组连续字符看：BIO 标签开启或延续实体，内部的 `flush()` 在样本边界把累计的字符和实体组织成带 ID 的样本。

回到 `prepare_data()`，三个集合组成字典，依次交给 `_deduplicate()`、`_apply_revisions()` 和 `_apply_exclusions()`。最后检查跨集原文重合，写出三份 JSONL、类别表和审计文件。训练端只根据 `config["data"]["processed_dir"]` 找成品文件。第 5 次实验配置指向 `data/processed-exam-results/`，基础清洗入口默认产出 `data/processed/`。两套数据的关系见[数据目录索引](../data/README.md)，运行命令见 [README](../README.md)。
