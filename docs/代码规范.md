# 代码规范与开发检查

本文用于日常开发。运行项目见 [README](../README.md)，模块和数据结构见[技术方案](中医药命名实体识别技术方案.md)。

## 1. 编写规则

使用 Python 3.12。文档和接口说明使用中文；函数、变量使用英文 `snake_case`，类使用 `PascalCase`，常量使用大写名称。

规则统一维护在 [pyproject.toml](../pyproject.toml)：

| 检查项 | 约定 |
|---|---|
| 格式 | Ruff 统一格式，目标行宽 100；不可自动折行的字符串、注释可超过此值 |
| 静态检查 | 检查基础语法、未使用变量、导入顺序、命名和常见错误 |
| 函数复杂度 | 圈复杂度上限 15，较复杂的流程按职责拆分 |
| 类型 | 生产代码函数提供参数和返回值注解 |
| 接口说明 | 公共模块、类和函数提供中文说明，按需注明输入、返回值、异常及副作用 |
| 测试 | 用行为名称描述断言；不强制每个测试函数重复写文档或类型注解 |

Ruff 能检查注解和文档字符串是否缺失，不能判断说明是否准确、易懂，仍需代码审查。

## 2. 类型与数据边界

业务结构优先使用 [ner_types.py](../ner_types.py) 中的 TypedDict。实体位置固定为 Python 字符索引 `[start, end)`。

TypedDict 不执行运行时校验。读取外部 JSON/YAML 后仍需校验：`read_jsonl()` 检查每行是否为对象，`validate_samples()` 检查标注样本；配置校验分布在加载与训练准备阶段，并非完整的配置 schema 校验。

mypy 当前检查配置中明确列出的 8 个生产模块，要求函数有类型注解。第三方动态接口和外部数据边界允许显式 `Any`，并忽略缺失的外部类型声明。因此，检查通过不等于所有数据都获得了严格类型保证。新增生产模块时应同步更新 mypy 文件列表。

## 3. 本地检查

先按 README 建立虚拟环境并安装适合本机的 PyTorch。激活环境后，安装开发依赖并执行：

```bash
source .venv/bin/activate
python -m pip install -r requirements-dev.txt

python -m ruff check .
python -m ruff format --check .
python -m mypy
python -m pip check
python -m pre_commit validate-config
OMP_NUM_THREADS=1 TOKENIZERS_PARALLELISM=false python -m pytest -q
```

需要调整格式时执行 `python -m ruff format .`。类型检查和测试均不需要下载模型，测试在本地构造随机微型 Qwen2。


## 4. 提交前检查

每个新克隆的仓库都需单独安装钩子：

```bash
python -m pre_commit install
python -m pre_commit run --all-files
```

[钩子配置](../.pre-commit-config.yaml) 使用当前 Python 环境中的开发工具，提交前应激活虚拟环境。它对涉及 Python 文件的提交执行静态、格式和类型检查，不自动修改文件，也不运行完整测试。

`--all-files` 检查 Git 已跟踪的文件。尚未加入 Git 的文件，用上一节的全目录命令检查。仅修改配置或文档时，也应按改动内容手动运行相关检查。

## 5. 持续集成

[GitHub Actions](../.github/workflows/quality.yml) 配置为在 push 和 pull request 时运行，使用 Python 3.12 与 CPU PyTorch，仓库权限为只读。检查包括依赖一致性、静态规范、格式、类型、钩子配置和完整测试。

CI 不覆盖 CUDA/QLoRA 和真实识别效果；已执行结果与尚未验证项统一记录在[开发验证记录](开发验证记录.md)。
